# Compiler Review 2026-07

Date: 2026-08-02

## Executive summary

The current compiler is a credible and well-structured Oberon-0 subset implementation with a clear pipeline, a meaningful test corpus, and a good foundation for incremental growth. It is already strong enough for teaching, experimentation, and validation of a substantial subset of the language. However, it is not yet a complete implementation of the full language described in Wirth’s Compiler Construction volumes, and it is not yet packaged as a deployable end-user compiler distribution.

Overall assessment:

- Strength: solid engineering baseline and good architecture direction.
- Gap: still a subset compiler, not a full page-63 implementation.
- Risk: future growth could become brittle unless the type system and diagnostics model are strengthened soon.
- Readiness for distribution: promising, but not yet production-ready as a standalone compiler package.

## 1. Completeness against Wirth’s compiler books

### What is already implemented well

The current compiler covers a meaningful portion of the Oberon-0-style language model:

- module structure with optional imports and optional module body
- basic statement forms: assignment, procedure calls, if/else, while
- simple declarations for constants, variables, procedures, and typed declarations
- builtin IO support for `WriteLn`, `ReadInt`, and `EOF`-style checks
- string literal support and builtin `WriteString`
- semantic validation for duplicate declarations, undeclared targets, arity, and basic type compatibility
- Rust code generation and an end-to-end golden test pipeline

This is already a useful compiler rather than a parser-only prototype.

### What is still incomplete relative to the Wirth reference

The current implementation is still partial compared with the full Oberon-0 language surface described on page 63 and in the accompanying compiler design material.

Important gaps remain:

- selectors and designators are not yet fully supported
- arrays and record types are not implemented
- several operators from the Wirth grammar are still missing or only partially supported
- relational operators and boolean logic are only partially implemented in the current subset
- `ELSIF` and `REPEAT ... UNTIL` are not yet present
- procedure parameters and declarations still need fuller parity with the reference syntax
- the current implementation is still closer to a “typed subset” than to a complete language implementation

### Verdict

The compiler is not yet complete against the Wirth reference, but it is moving in a sensible order. The roadmap and the alignment matrix are both realistic and well-scoped. The current state is best understood as a strong Milestone A/B foundation rather than a finished language implementation.

## 2. Language stability and test coverage

### Strengths

The repository already has a respectable test foundation:

- unit tests for scanner, parser, semantic analysis, lowering, and code generation
- corpus-driven parser tests for valid and invalid inputs
- semantic corpus tests for valid and invalid programs
- golden end-to-end tests that compile and execute generated Rust projects

The current `cargo test` run completed successfully with 206 tests passing, which is a solid sign that the current subset is stable enough for continued development.

### Where coverage is still thin

The present tests are good, but they do not yet fully cover language stability in the broader sense.

The main gaps are:

1. Feature breadth coverage
   - The corpus mostly exercises the implemented subset well, but the coverage is not yet broad enough for all language constructs that are expected to be part of the long-term Oberon-0 target.

2. Cross-feature integration tests
   - There are good unit and golden tests, but fewer tests that combine multiple language features in realistic programs.

3. Regression focus around roadmap milestones
   - The tests cover many current features, but they do not yet strongly encode the roadmap transitions for arrays, records, and full type checking.

4. Diagnostics stability
   - Error reporting is present, but there is less evidence of a broad, durable test suite that locks down exact diagnostic behavior across the whole compiler pipeline.

### Recommendation

The test base should be expanded in three directions:

- more negative tests for parser and semantic edge cases
- more integration tests that mix declarations, control flow, and typed expressions together
- more regression tests that describe the intended language behavior before implementing new features

### Verdict

The test foundation is already strong enough for the current subset, but not yet strong enough to confidently claim full language stability for Oberon-0 as a whole.

## 3. Architecture and maintainability

### What is strong

The source structure is already fairly solid for a compiler project of this size:

- clear stage separation: scanner, parser, semantic analysis, lowering, code generation
- dedicated AST, HIR, symbol, and manifest modules
- a separate lowerer that translates semantic structures into HIR instead of mixing everything together <!-- cspell:disable-line -->
- tests aligned with each stage of the pipeline

This is the right structure for sustainable growth. It is much better than a single monolithic parser/compiler file, and it gives the project a good chance to evolve without becoming unmaintainable.

### What should be improved

The architecture is promising, but a few areas need strengthening before the project can grow comfortably toward a full compiler.

Priority concerns:

1. Type system consolidation
   - The current compiler has typed declarations and some semantic type checks, but the type model is still not yet fully centralized.
   - This is the single biggest architectural risk for future growth.

2. Diagnostics and error propagation
   - Error handling is functional, but it would benefit from a more structured diagnostic model with source spans and richer context.

3. Lowering and code generation coupling
   - The project already separates stages, but some lowering and code generation behavior still depends on implementation details that could become harder to evolve.

4. Explicit architecture boundaries for future features
   - Arrays, records, and later language constructs will become much easier to implement if the type system and HIR become more explicit and less ad hoc.

### Verdict

The architecture is good enough for continued development and is already stronger than many early-stage compiler prototypes. It is not yet fully “future-proof,” but it is on a healthy trajectory if the type system and diagnostics are formalized next.

## 4. Improvements needed to build a strong and proper Oberon-0 implementation

The following improvements are the most important next steps.

### Highest priority

1. Formalize a shared type model
   - Introduce a central representation for scalar types, aliases, arrays, records, and procedure signatures.
   - Make type compatibility checks flow through a single logic path.

2. Strengthen semantic analysis
   - Move from “name resolution plus targeted checks” toward a fuller semantic pass that understands expression typing, assignability, and designator validity.

3. Improve diagnostics
   - Add source locations, better error messages, and consistent diagnostic codes across scanner, parser, semantic, and lowering stages.

4. Complete the roadmap features in the intended order
   - Arrays, records, typed formal parameters, and full operator coverage should be implemented in a disciplined sequence rather than as isolated patches.

### Medium priority

1. Add more end-to-end examples
   - Especially examples that combine declarations, control flow, modules, imports, and new data structures.

2. Add stronger regression coverage for long-term language stability
   - This should be treated as part of implementation quality, not just as a test afterthought.

3. Improve packaging and developer ergonomics
   - Make it easier to install and run the compiler outside the repository checkout.

### Verdict

The compiler is already good enough to continue building on, but the most important architectural improvement is to make the type system and diagnostics model explicit and durable. That will have the greatest impact on the quality and sustainability of the implementation.

## 5. Deployability without compiling from source first

### Current status

The current setup is not yet sufficient for a true deployable compiler distribution.

Why:

- the repository is primarily source-first and requires a Rust toolchain to build
- the documented workflow is based on `cargo build`, `cargo run`, or local source checkout usage
- there is no evidence of prebuilt release artifacts for Linux, macOS, or Windows
- the compiler is not yet presented as a packaged installable toolchain for end users

### What is already positive

- the project already has a clear CLI entry point
- examples and scripts are in place
- the compiler can generate runnable Rust projects, which is useful for downstream usage

### What is missing for real deployability

To make the compiler usable without compiling sources first, the project should add:

- prebuilt binaries for major platforms
- a simple installation path such as a shell script, package manager integration, or GitHub Releases workflow
- versioned release artifacts and checksums
- a clearer distribution story for both the compiler and generated Rust targets

### Verdict

The current setup is suitable for developer use in a repository checkout, but it is not yet sufficient as a standalone, deployable compiler distribution for general users.

## Final verdict

The current compiler is a promising and credible Oberon-0 subset implementation with a strong enough foundation to continue growing. The architecture is good, the test base is meaningful, and the roadmap is sensible. The main weaknesses are not in the basic structure, but in completeness relative to the Wirth reference, the maturity of the type system, and the absence of a proper deployment story.

If the project continues with disciplined implementation of the roadmap and strengthens type handling and diagnostics, it can become a strong and proper Oberon-0 compiler rather than just a useful prototype.
